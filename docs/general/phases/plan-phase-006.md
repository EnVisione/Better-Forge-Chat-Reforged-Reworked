## Purpose and Ownership

This phase freezes the final post-change SEF 2 candidate and proves it through the complete clean-checkout verification matrix. It owns `SEFAUD-REQ-008`: maintained static quality gates, Java 21 build reproducibility, generated-reference and performance drift, all required GameTests, dedicated-server operation, enhanced and fallback client compatibility, mixed multiplayer, optional-provider behavior, graphical and textual UI, packet abuse, lifecycle revocation, persistence interruption and recovery, performance, final artifact inspection, complete-diff inspection, evidence invalidation, and a final full rerun after the last product or verification-system change. Portable behavior is evidenced through the Minecraft Java client fixture and shared runtime workflows. Direct macOS or Windows evidence is required only for changed or exercised non-client clean-build, provider, recovery, native-writer, dependency-loading, or packaging rows. Linux, macOS, and Windows remain supported targets, and shared portable code paths are not duplicated solely by host.

The master plan owns product scope, compatibility pins, the defect boundary, phase order, and final completion authority. `SEFAUD-PHASE-005` owns the last change-stage lifecycle and integration repairs. This file owns only the final verification system and evidence execution for Phase 006. It may add or repair maintained verification gates, fixtures, deterministic harnesses, and evidence capture required by `SEFAUD-REQ-008`. It does not authorize unrelated product work, a platform upgrade, publication, deployment, production mutation, or a lower-fidelity substitute for a blocked real workflow.

The **final candidate revision** is the integrated `SEFAUD-PHASE-005` result after all change-stage requirements pass. It becomes provisionally frozen at Phase 006 entry. A failed row is not patched around in the evidence ledger. A confirmed product defect reopens its canonical owner phase, unfreezes the candidate, and invalidates every dependent Phase 006 result. A defect limited to the release-verification system is repaired in this phase, but the repair invalidates every result affected by the changed gate, fixture, task, environment definition, or evidence schema. The **final verified revision** is the integrated Phase 006 result after the complete matrix has rerun following the last change. Phase 007 may consume only that revision and its artifact hashes. `EXT-001` environment manifests and runtime results and `EXT-002` platform-dependency provenance and advisory closure are independent records. Neither can stand in for the other. Unknown, partial, unavailable, or failed conditional evidence leaves affected rows open, while a direct mod-owned vulnerability or exercised host-specific path without required proof blocks Phase 006 exit and the plan endpoint without narrowing supported scope.

### Ordering, Failure Handling, and Safe Parallelism

- Tasks 001 and 002 are hard gates. Do not start expensive runtime work with an unintegrated candidate, ambiguous lineage, dirty tracked checkout, unsafe staging root, missing mandatory fixture for an exercised path, incomplete applicable `EXT-001` manifest, unavailable required `EXT-002` inputs, or noncompliant `check` lifecycle. Missing applicable prerequisites block affected phase exit and the final endpoint, while unblocked portable preparation may continue.
- Task 003 establishes the build artifact used by all later tasks. Runtime environments copy that artifact by digest; they do not rebuild independently with different inputs.
- Task 004 must finish before manual matrices so a missing GameTest cannot be disguised by an unrelated runtime pass.
- Tasks 005 through 012 may run concurrently only in independently named, host-attributed, and path-confined environments. Admission needs multiple clients in one environment; those clients are coordinated participants, not separate test roots. No other task shares that server. The Minecraft Java client fixture is the client evidence surface. No operating system specific client evidence is required. macOS and Windows results remain distinct only for changed or exercised non-client host-specific paths; directory naming, copied logs, containers, compatibility layers, or mocked OS properties do not prove a different host.
- A failed row records exact expected/actual behavior, decisive bounded logs, commit, artifact digest, environment, fixture, and invalidation set. Retrying creates a new attempt. It does not overwrite or relabel the failed attempt.
- A product defect stops every dependent row and is routed to its canonical owner phase. Phase 006 resumes only after sequential reintegration and a new candidate freeze. A verification-system defect may be repaired here, but all affected results and the final artifact are discarded and regenerated.
- Process interruption uses an exact recorded task-created PID and disposable root. Normal shutdown proof always runs separately. Never send a signal using a broad process match or touch a production process.
- Cleanup removes only task-created disposable paths recorded in Task 001 after evidence retention requirements are met. It never targets the repository root, user home, unrelated untracked paths, or an unresolved variable.

## Architecture and Implementation Boundaries

### Verification Authority and Evidence Flow

Authority flows from the integrated source and build inputs to one built artifact, then to isolated runtime environments, raw evidence, sanitized row results, and the final ledger. Documentation, a historical hash, a previous phase pass, or a manually edited status table cannot create a passing result. Each record contains commit, artifact hashes where applicable, exact command/workflow, Java/platform versions, fixture identity, expected result, actual result, disposition, raw-evidence reference, and invalidated-by set.

Each runtime record also carries an immutable host key that joins to exactly one `EXT-001` Linux, macOS, or Windows environment manifest. The manifest must prove actual host execution through OS version and architecture, filesystem, Java runtime, Minecraft and NeoForge versions, wrapper command, resolved runtime identities, fixture ids, timestamps, and evidence-root identity. A filesystem path, runner label, user-entered platform string, or another host's copied output is not host identity. Linux is canonical for portable behavior. The set is conjunctive across Linux and each macOS or Windows path that is changed or exercised.

The maintained test system must separate deterministic fast gates from high-fidelity runtime gates without allowing the former to replace the latter. `check` owns formatting, warning zero growth, static analysis, unit tests, and maintained coverage. Named Gradle/runtime workflows own GameTests, server, clients, providers, graphical tests, recovery, and profiling. CI must call the stable deterministic gates appropriate to pull requests; the Phase 006 completion packet additionally proves the expensive local or approved staging workflows.

### Static Analysis, Warnings, and Coverage

Formatting is repository-wide for maintained Java and build sources but does not rewrite unrelated files merely to adopt a tool. The initial formatter application must be scoped and reviewable; unrelated mass reformatting is not acceptable. Compiler warnings use a reviewed baseline or equivalent zero-growth mechanism: existing warnings receive identities and dispositions, new warnings fail, and removal tightens the baseline. Static-analysis rules prioritize correctness, concurrency, resource lifecycle, null/state safety, path handling, serialization, permission checks, side boundaries, and ignored failures. Suppressions are narrow, colocated or centrally attributable, explain the invariant, and fail review if broader than necessary.

Risk-based coverage uses the Phase 001 trust-boundary and Phase 002 persistence ownership matrices. It requires line and branch coverage for security- and persistence-critical code and direct contributors, with explicit exception review for Minecraft-only glue that must be covered by GameTest or runtime proof. Coverage percentages are not a substitute for branch identity: permission denial, stale revision, provider failure, corruption, timeout, rollback, and duplicate-side-effect branches must have named tests even if aggregate numbers pass.

### Runtime Topology and Logical-Side Boundaries

Every dedicated server uses only common/server classes. A server startup that logs or masks `net.minecraft.client` classloading fails. Matching enhanced clients may load presentation packages and negotiate only server-advertised feature bits. The fallback client uses `fallbackRuntime` with main mod output excluded; its successful join proves the universal JAR remains optional, not that it contains server authority. An incompatible client fixture changes only protocol compatibility inputs and must never be allowed to mutate server state through unsupported features.

Server authority remains current for identity, permission, target, policy, revisions, persistence, and mutation. Client screenshots and caches are presentation evidence. Provider fixtures, GUI projections, generated references, diagnostics, recovery files, and replayed payloads never become authority. Network handlers validate bounds and schedule onto the correct logical thread before mutation.

### Fixtures, Concurrency, and State Isolation

Use the synthetic actors and roles from `test.md`. UUIDs, names, provider records, messages, addresses, inventory items, and worlds are fixture-owned. Each environment gets its own server config, world, mods set, client game directories, provider data, port range, and evidence namespace. Concurrent tests declare barriers and expected ordering. Admission FIFO, duplicate login, persistence coalescing, permission revocation, panel submission, and shutdown races use deterministic synchronization or observable server events, not arbitrary sleep as proof.

All destructive storage work begins from an immutable snapshot with preflight hashes and operates under a canonical disposable root. The test harness identifies exact interruption points around publication, journal/receipt state, game effect, and flush. Recovery uses the product's documented procedure, not manual editing that bypasses validation. Migration and rollback retain the old JAR/data snapshot pairing.

### Artifact, Dependency, Resource, and License Boundaries

The final artifact comes from the clean verified source with the pinned version. Inspect both declared and resolved configurations and compare them with embedded JAR entries and the installed NeoForge runtime on canonical Linux and on each affected or exercised macOS or Windows non-client host-specific path. Compile-only integrations must not become unintended bundled implementations. JNA and JNA Platform may remain compile only when the exact pinned runtime supply, API and binary compatibility, and native loading pass on each executed host path. Any JNA class or native library embedded by the mod is a duplicate-runtime failure. Reconcile `src/main/templates/META-INF/neoforge.mods.toml`, `src/main/resources/sef.mixins.json`, `src/main/resources/META-INF/accesstransformer.cfg`, generated resources, language assets, service metadata, and every packaged license obligation. Duplicate entry names, conflicting duplicate classes, local absolute paths, logs, run directories, caches, crash reports, evidence, private keys, tokens, or environment files fail.

`EXT-002` is not a subsection of `EXT-001`. Its packet independently proves authoritative NeoForge repository origin, artifact coordinates, versions, digests, licenses or provenance, compile and runtime paths, JNA supply, and separate candidate-graph, packaged-mod-artifact, installed-runtime-artifact, affected-API-reachability, authoritative-advisory-applicability, and compatible-remediation dispositions. No alert may pass through suppression, ownership transfer, absence from the mod JAR alone, a development override, or narrowing Linux, macOS, or Windows scope.

### Platform-Native Opened-Object Boundary

On canonical Linux and each affected host-specific path, the native audit writer must prove that type, link or reparse state, identity, and link count are obtained from the descriptor or handle that is then mutated and held through flush. Linux and macOS may share POSIX source only when each host independently proves its flags, structure layout, descriptor identity, link behavior, write, flush, rotation, and restart. Windows must independently prove handle identity, reparse state, link count, object stability, write, flush, rotation, and restart. A pre-open or post-open path check, path equality, canonical path, or path-only fallback cannot establish opened-object identity. Unsupported metadata fails closed and preserves prior valid state; it never turns Windows or another target into unsupported scope.

### Performance and Operational Boundaries

Deterministic metadata generation remains off the logical server tick and suitable for a maintained gate. Live profiles cover server tick, persistence, provider refresh, admission, command bursts, payload transfer, GUI/HUD updates, and disguise rendering at representative loads. Measurements record hardware, OS, JVM, flags, player/client count, duration, warmup, workload, and profiler. A performance failure cannot be waived solely because another machine is faster. Diagnose environment variance and rerun the same controlled workload.

Evidence capture is bounded. Do not retain unbounded debug logs or per-tick spam. Capture the decisive window, structured counters, profiles, screenshots, and short recordings. Sanitization removes secrets, personal data, and private host paths while preserving stable repository-relative or evidence ids.
