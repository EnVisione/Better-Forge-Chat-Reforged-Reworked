## Purpose and Ownership

This phase closes `SEFAUD-REQ-004` by deriving the authoritative executable administrator-action inventory from the frozen live Brigadier dispatcher, sealed command catalog, active shortcut registry, current module state, and actual command owners, then proving every resulting action across authorization, source, target, input, effect, failure, persistence, equivalent route, feedback, audit, redaction, and operating-system evidence behavior. Every confirmed command defect is repaired and proved at its real failure boundary. The universal matrix records Linux as the canonical evidence host for portable action semantics, with direct macOS or Windows evidence only for changed or exercised host-specific audit, filesystem, startup, shutdown, restart, or packaging paths under conditional `EXT-001`.

The master plan owns product scope, owner decisions, phase topology, compatibility boundaries, and completion authority. This execution blueprint owns only the detailed execution of `SEFAUD-PHASE-003`. Phase 000 owns the baseline inventory format and stable row identity. Phase 001 owns closed security and dependency boundaries. Phase 002 owns durable state and cross-store guarantees. This phase consumes those contracts and must reopen an upstream gate when executable behavior reveals an omitted route, authority boundary, durable owner, or cross-store invariant.

Registration, a successful parse, command-tree visibility, catalog membership, or execution of a safe read-only route proves only that specific layer. None proves authorization at mutation time, the exact effect, persistence, failure atomicity, feedback, audit, redaction, or equivalent-route behavior. Phase closure requires the highest-fidelity evidence declared for each action row.

This is an audit plus mandatory in-scope remediation phase under `DEC-001`. Under `DEC-002`, the sixteen intentionally unavailable control families remain unavailable negative contracts and are not implementation scope. Destructive and privacy-sensitive workflows use disposable synthetic environments only under `DEC-005`. No work in this phase publishes a release, deploys to production, handles production credentials, changes the pinned platform, or adds unrelated functionality.

## Architecture and Implementation Boundaries

### Inventory and canonical ownership

- The runtime-derived action inventory is authoritative for executability. Build it after command registration and module publication from the live Brigadier tree, sealed `CommandCatalog`, active `ShortcutRegistry`, module state, automation publications, server-control handler state, GUI descriptors, and actual registrar ownership. Generated references and historical counts are reconciliation inputs, not membership authority.
- One executable behavior maps to one stable canonical action id. A live route without a catalog owner, a catalog action without a valid live route, an active shortcut without a registered root, or two owners claiming one canonical route is a phase-blocking defect unless the master explicitly excludes it.
- The universal row records at least stable row id, action id, canonical route, ordered equivalent routes, owning registrar and domain, module state, access and audit class, every permission and bypass, absent, deny, grant, inherited, wildcard, revoke, refresh, outage, reload, and reconnect result, every allowed and denied source, target behavior, argument schema and hard bounds, feature, quota, cooldown, cost, warmup, confirmation and revision fields, exact success effect, every declared failure and zero-side-effect oracle, durable-owner and restart join, feedback class, audit event and sink path, redaction class, unavailable-family disposition, Minecraft Java client fixture and canonical Linux evidence status and references, conditional macOS or Windows non-client host-specific status where applicable, shared-path justification or direct-host requirement, native provider and runtime dependency join where audit state is emitted or persisted, test layers, evidence, and invalidation dependencies.
- Nonapplicability is explicit and justified. For example, a console-only no-target diagnostic may mark hierarchy not applicable, but it may not omit source denial, feedback, audit, or discovery proof.

### Authority and execution order

- Brigadier visibility and suggestions are least-privilege projections. They must not disclose hidden identities, private records, unavailable internal state, or actions the current source cannot execute. Visibility is not authorization.
- Immediately before mutation, the logical server rechecks the canonical action, current module and feature state, source class, actor identity, permission and provider revision, hierarchy, exemptions, target visibility and freshness, quota, cooldown, cost, warmup, confirmation, and relevant configuration, profile, record, command-tree, and session revisions.
- `CommandExecutionService` and domain-specific policy helpers remain the common enforcement boundary. A direct registrar, shortcut, GUI hook, alias, bundle, sudo path, panel, profile, scheduled job, or integration may narrow authority but never bypass or broaden it.
- Temporary or delegated authority is scoped to the bound action, actor, target, source, parameters, revisions, and one execution where declared. It cannot mint durable permission, outlive expiry or disconnect, authorize nested wrappers, or escape to another root.
- Server-owned sources and stored command text are not authority by themselves. Their construction, permission profile, root allowance, target scope, and audit attribution must be explicit and current.

### Inputs, effects, and persistence

- Brigadier constrains syntax. Domain validation owns semantic bounds, registry availability, target state, quotas, compatibility, and race checks. Parsing a namespaced value or a long string does not prove that the domain accepts, applies, rejects, persists, or safely reports it.
- Each action has an effect oracle independent of command feedback. The oracle observes authoritative domain state, game state, inventory or economy state, durable records, queue or journal state, and relevant projections before and after execution.
- Validate all targets and all bulk elements before an all-or-nothing mutation. If an action deliberately supports partial completion, the row must name the per-target result, ordering, idempotency, compensation, persistence, and audit contract; accidental partial success is a defect.
- Persistent commands use Phase 002 owners and operation protocols. Nonidempotent effects carry stable operation identity or another verified duplicate-prevention contract. A storage error never becomes a successful command merely because an in-memory or game effect occurred.
- Clean restart, corrupt-state recovery, unsupported-newer state, and rollback follow the verified owner contract. Command tests must not weaken storage safety by deleting or recreating authoritative files on failure.

### Equivalent routes and feedback

- Canonical, shortcut, GUI, fallback, alias, bundle, sudo, panel, profile, scheduled, and approved integration paths retain one canonical action id, policy and cooldown identity, exact normalized parameters, target set, effect, result class, actor attribution, audit class, and redaction rule.
- Alias and bundle publication preserves access and audit strength, source restrictions, recursion limits, root ownership, expansion bounds, and revision checks. Runtime execution revalidates the expanded canonical actions; compile-time approval alone is insufficient.
- Preview and confirmation are immutable, expiring views of current server authority. Any bound field or revision change requires a new preview and token. Replaying a consumed token or switching route fails without acquiring a lasting cooldown, cost, or domain mutation.
- Feedback is product UI under `DEC-008`. Use structured components, stable labels, actionable bounded failure detail, safe target naming, and consistent success and denial hierarchy. Do not leak restricted arguments, hidden identities, raw addresses, private messages, host paths, tokens, provider internals, or stack traces.
- Mandatory audit records real actor, effective actor where different, source type, canonical action, targets or safe target metadata, result, reason, duration, origin, definition and policy revisions, provider context, correlation, audit class, and redaction disposition. Optional observation cannot weaken or replace mandatory audit.

### Compatibility, concurrency, and performance

- Preserve the pinned platform and current public ids. If remediation must change a route, permission id, action id, serialized definition, protocol field, or persistent schema, implement the smallest backward-compatible adapter or versioned migration and document exact rollback behavior.
- Permission refresh, reload, reconnect, module change, target change, confirmation expiry, and concurrent execution are adversarial scheduling points. Tests use barriers or latches so the decisive recheck is observable rather than timing-dependent.
- Catalog-wide tests may share a policy harness only when the same code path and invariant are genuinely common. Every action still needs an owned row, action-specific source and target applicability, an effect or read-only oracle, feedback and audit proof, and highest-required-fidelity execution.
- Keep command registration, discovery, suggestion generation, permission resolution, target selection, bulk iteration, bundle expansion, audit emission, and feedback bounded. No filesystem or network access, blocking provider call, unbounded scan, or unbounded allocation belongs on a command, tick, network, or suggestion hot path.
- Large-matrix execution is sharded deterministically by stable action id. Sharding must preserve one complete result per row, reproducible ordering, bounded logs, and fail the aggregate when a shard is missing, duplicated, stale, blocked, or executed at a different product revision.

### Cross-platform command and audit execution contract

- Every executable-action and unavailable-family row has a canonical Linux server cell and an explicit client applicability field. Only a client-exposed route receives a Linux Minecraft Java client-fixture cell; a server-only row records `NOT_CLIENT_APPLICABLE` with its source and side rationale. No macOS or Windows client cell exists. A conditional macOS or Windows non-client cell is added only when a host-specific path is changed or exercised. Applicable execution cells are `DIRECT_PASS`, `SHARED_PASS`, `FAIL`, or `REQUIRED_HOST_EVIDENCE_PENDING`. `SHARED_PASS` names the covering direct evidence row, identical portable Java owner and call path, invariant, and absence of host-sensitive behavior. `REQUIRED_HOST_EVIDENCE_PENDING` is mandatory in-plan work and never becomes excluded, skipped, unsupported, or an external blocker.
- Direct evidence is mandatory whenever the command path depends on operating-system launch or input behavior, native loading, filesystem semantics, security-sensitive audit append or publication, rotation, directory handling, flush, bounded shutdown, restart, or installed runtime packaging. A common interface or unit test does not prove its Linux, macOS, or Windows provider.
- Every audit-emitting action row names whether mandatory audit remains in memory, enters the command journal, enters an optional file sink, queues asynchronous publication, rotates a file, flushes during execution, or flushes during shutdown. The row joins each used path to the exact audit event schema, result class, provider implementation, resolved runtime dependency identity, opened-object identity record, durable artifact, restart result, and failure behavior.
- Native evidence may be shared between command rows only when the writer, sink, result class, append mode, rotation state, failure cut point, dependency identity, provider implementation, and filesystem invariant are identical. The matrix validator records the covering native-evidence row and rejects a broad provider pass that omits a distinct command-specific payload or persistence path.
- Phase 003 consumes the closed `EXT-002` platform provenance and advisory packet from Phase 001. It revalidates exact runtime supply and native loading on canonical Linux and on each macOS or Windows host whose changed or exercised non-client path triggers `EXT-001`, then inspects the candidate JAR for duplicate JNA classes or native libraries. A non-exercised host path receives a source-to-artifact `NOT_EXERCISED` disposition. Any graph, version, ABI, packaging, advisory, or provider drift reopens Phase 001 and blocks this phase. `EXT-001` and `EXT-002` remain in-plan closure work, never permanent external blockers.
