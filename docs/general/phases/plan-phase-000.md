## Purpose and Ownership

This phase freezes the reproducible SEF 2 audit baseline that every later phase consumes. It derives complete inventories from the candidate source, live registries, dispatcher, runtime diagnostics, build graph, packaged artifact, tests, generated references, and current documentation. It reconciles exact identities rather than accepting historical counts. Every in-scope surface receives one stable row, one canonical owner, one later-phase disposition, one evidence route, and an explicit invalidation set.

The sole canonical requirement is `SEFAUD-REQ-001`. The master plan owns the product scope, decisions, phase topology, compatibility boundary, and endpoint. This file owns only `SEFAUD-PHASE-000` and tasks `P000-TASK-001` through `P000-TASK-014`. Phase 000 may implement or repair inventory machinery, evidence controls, and the shared diagnostics contract required to make the baseline observable. It does not perform the security, command, UI, persistence, integration, or release remediation assigned to later phases. A product defect discovered here receives a stable finding and is routed to its canonical phase. An inventory, diagnostics-foundation, evidence-schema, reconciliation, or drift-gate defect remains owned here and blocks Phase 000.

`EXT-001` and `EXT-002` are available mandatory in-plan work, not external-owner dependencies and not permanent blockers. Phase 000 defines their complete row schemas, discovers current availability and reachability, performs its owned baseline evidence, and routes the remaining phase-specific closure work. A failed required predicate is an ordinary failed phase row. A host-specific row that the frozen candidate does not exercise is closed as `NOT_EXERCISED` with source-to-runtime reachability evidence, never as unsupported. A direct mod-owned dependency exposure remains open for Phase 001 remediation; an upstream-only platform alert may become `NOT_MOD_RESOLVABLE` only after all ownership and reachability dimensions are proved.

The execution-base revision and frozen audit-baseline revision are distinct:

1. The execution base is the approved integrated candidate from which the Phase 000 branch is created. It must descend from `0c75bf25c58622096dfa7cc65a5f4b32e6d60ac4` and must not silently import the legacy `forge-1.20.1` line.
2. The frozen audit baseline is the merged Phase 000 result after the last inventory, diagnostics, schema, test, generated-reference, or documentation correction. Downstream evidence binds to its merge commit, artifact SHA-256 and SHA-512, and signed annotated phase tag.

### Security Boundary Completeness Rules

The boundary inventory must explicitly cover credentials and tokens, private messages, raw or linkable addresses, hidden and vanished identities, restricted moderation reasons, command arguments subject to redaction, private GUI projections, native filesystem paths, provider metadata, and audit evidence. Inventorying a source or sink without the connecting flow and validator is incomplete.

## Diagnostics and Debugging

**Requirement IDs:** `SEFAUD-REQ-001`
**Task IDs:** `P000-TASK-010`, `P000-TASK-011`, `P000-TASK-013`
**Controls:** Planned controls are `/sef debug on <category> [target] [seconds] [sample_limit]`, `/sef debug status`, and `/sef debug off`; the dedicated server console and sources with `sef.commands.sef.debug` may use them, diagnostics default off, unknown categories and unauthorized or absent targets are rejected, and `off` is idempotent.
**Signals:** Emit versioned, structured, sanitized observations for capture identity, sequence, correlation, logical side, category, component/action, pseudonymous actor and effective actor, revision, expected and actual decision, reason code, duration in milliseconds, payload bytes, queue depth, drop/truncation counters, storage/writer/protocol state, and expiry.
**Collection procedure:** Use the numbered Phase 000 procedure below to bind one bounded capture to the candidate, fixture, inventory rows, exact stimulus, before/after state, retained support packet, and verified teardown.
**Headless verification:** On `node-1` or the laptop, after inspecting the Gradle task graph to prove no client or renderer starts, run focused diagnostics and inventory tests, `generateAuditInventory`, applicable server-only GameTests, and a disposable no-GUI dedicated-server capture; assert authorization, schema, lifecycle reset, bounds, redaction, correlation, no mutation, and exact inventory joins.
**Client verification:** Only the Linux laptop client fixture verifies client registration, receipt, screen/HUD signal ownership, input-side correlation, disconnect/reset, and the absence of server-only substitution. **Client audio isolation:** Before launch, set and read back the disposable instance master audio as zero. Bind the exact owned Hyprland window address, class, title, and PID with `hyprctl clients -j`; correlate only that process tree to its PipeWire or PulseAudio application stream; mute it with `wpctl` or `pactl`; and verify the stream reports muted before assertions. Monitor every stream recreation and mute each replacement. Teardown stops the watcher and client and removes only owned temporary audio state. Never mute default or system-wide audio.
**Budgets and privacy:** Default duration is 60 seconds, maximum duration 300 seconds, default sample limit 1,000 events, maximum sample limit 10,000 events, maximum output is 4 MiB, and accepted rate is capped at 100 events per second per capture; disabled mode performs no material formatting, traversal, packet, allocation, or filesystem work; credentials, tokens, private messages, raw addresses, hidden identities, restricted arguments, artwork bytes, and private absolute paths are redacted.
**Regression and support:** Maintained tests fail on schema drift, bypass, leaked fields, missing correlation, unbounded capture, stale enablement, reset failure, hot-path disabled allocation, excessive enabled overhead, changed gameplay, or false success. `DOCUMENTATION.md`, generated command and permission references, and the Phase 000 support packet document enable, reproduce, status, disable, locate, redact, recover, and submit steps without automatic upload.

The diagnostics system is observation-only. It cannot grant authority, select an unvalidated target, change a policy result, alter a command result, mutate game or durable state, or become a retry path. Enabling creates a random opaque `capture_id`, freezes category and optional target scope, and reports remaining duration, event count, byte budget, rate, output route, drops, and truncations. Timeout, reload, stop, restart, disconnect, or target removal disables the applicable capture. Category extensions use the central schema and sanitizer.
